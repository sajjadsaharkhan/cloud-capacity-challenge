# ADR-0001: سرویس ظرفیت را رزرو می‌کند؛ ساخت سرویس را orchestrate نمی‌کند

- وضعیت: Accepted
- تاریخ: `2026-11-16`
- مرتبط: [PRD A-1, A-2, A-3](../prd/PRD.md#7-assumptions)، [ADR-0017](0017-no-workflow-engine.md)

## زمینه

صورت مسئله «هستهٔ backend سیستمی که این فرایند را مدیریت می‌کند» را می‌خواهد، اما ساخت واقعی VM و زیرساخت خارج از محدوده است. امروز این فرایند میان چند ابزار پخش شده و خطاهایی که صورت مسئله نام می‌برد به ظرفیت (دیده شد ولی دیگر نیست)، وضعیت درخواست (نتیجهٔ نامشخص) و کارهای رهاشده مربوط‌اند. اینکه مالک داده‌های ظرفیت فیزیکی کیست، مشخص نشده است.

## تصمیم

این سرویس مالک **ظرفیت قابل فروش (sellable capacity)**، **سهمیه‌ها** و **چرخهٔ عمر رزرو** است. سرویس‌های محصول (VM، DBaaS، IP) منابع را خودشان provision می‌کنند و از طریق hold، confirm، cancel و release با این سرویس صحبت می‌کنند، به سبک try-confirm-cancel. ظرفیت فیزیکی از طریق admin API یا یک sync job وارد می‌شود؛ این سرویس منبع حقیقت برای چیزی است که می‌توان فروخت.

## گزینه‌های بررسی‌شده

| سطح | گزینه | نتیجه |
| --- | --- | --- |
| 1 | یک سرویس CRUD که هم ظرفیت را ذخیره می‌کند و هم «سرویس را می‌سازد»، با یک ستون status | رد شد. دو مسئولیت یک وضعیت نیمه‌کاره را به اشتراک می‌گذارند: دقیقاً همان «فرایندی که هرگز تمام نمی‌شود» در صورت مسئله. |
| 2 | سرویس رزرو با قراردادی به سبک TCC؛ provisioning در جای دیگر | **انتخاب شد** |
| 3 | سرویس placement کامل در سطح host (traits، bin-packing، مانند OpenStack Placement) به‌همراه یک scheduler | فعلاً رد شد. به inventory زندهٔ hostها و یک تیم اختصاصی نیاز دارد؛ هیچ چیزی در صورت مسئله placement در سطح host را برای منابع تقسیم‌پذیر لازم نمی‌کند. |
| — | یک facade روی سیستم‌های موجودی که مالک ظرفیت‌اند | رد شد. بدون مالکیت شمارنده‌ها نمی‌تواند بررسی و برداشت را اتمیک کند، پس «دیده شد ولی دیگر نیست» باقی می‌ماند. |

## پیامدها

- اضافه کردن یک محصول یک تغییر داده است: یک ردیف محصول که resource classهایش را فهرست می‌کند.
- شمارنده‌ها fragmentation را نمی‌بینند؛ این با یک حاشیهٔ رزروشده کاهش می‌یابد ([ADR-0002](0002-resource-model.md)).
- ظرفیت فقط وقتی برمی‌گردد که سرویس‌های محصول release را صدا بزنند؛ یک رابط reconciler فراخوانی‌های ازدست‌رفته را پوشش می‌دهد ([spec 09 §6](../specs/09-admin-api.md#6-reconciliation-report)).

## زمان بازنگری

- وقتی خطاهای provisioning ناشی از fragmentation از حدود 1% confirmها بیشتر شود، یا یک محصول multi-GPU اضافه شود: poolها به سطح host منتقل شوند (تغییر داده).
- وقتی سازمان تصمیم بگیرد سیستم دیگری منبع حقیقت برای ظرفیت قابل فروش باشد: این سرویس به یک لایهٔ رزرو روی شمارنده‌های آن سیستم تبدیل می‌شود.
