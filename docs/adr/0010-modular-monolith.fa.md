# ADR-0010: Modular monolith با سه نقش اجرایی

- وضعیت: Accepted
- تاریخ: `2026-11-16`
- مرتبط: [معماری](../architecture/backend-architecture.md)، [ADR-0023](0023-clean-architecture.md)

## زمینه

حالت ظرفیت، سهمیه و رزرو باید در یک تراکنش تغییر کنند. این سرویس در مسیر ساخت سرویس استفاده می‌شود و اجرای آن باید برای ارزیاب ساده باشد.

## تصمیم

یک repository، یک build و یک container image، با ماژول‌هایی (Reservations، Capacity، Catalog، Admin، Jobs) درون یک clean architecture. این image در سه نقش اجرا می‌شود که با پیکربندی انتخاب می‌شوند: `api`، `sweeper`، `relay`.

## گزینه‌های بررسی‌شده

| سطح | گزینه | نتیجه |
| --- | --- | --- |
| 1 | یک process که همه‌کار را با timerهای درون حافظه انجام دهد | رد شد. timerها با مردن process از بین می‌روند؛ API و کارهای پس‌زمینه را نمی‌توان جداگانه scale کرد. |
| 2 | Modular monolith، سه نقش، تمام state در PostgreSQL | **انتخاب شد** |
| 3 | یک microservice برای هر دامنه (سهمیه، ظرفیت، رزرو، رویدادها) | رد شد. یک مرز سرویس از وسط تراکنش اصلی می‌گذراند و saga لازم دارد، بدون هیچ دلیلی از نظر scale یا تیم. |

## پیامدها

- scale افقی با اضافه کردن instanceهای `api`؛ نقش‌ها مستقل از هم scale می‌شوند.
- هر instance را می‌توان در هر لحظه kill کرد؛ بازیابی به هیچ هماهنگی‌ای نیاز ندارد.

## چه زمانی بازنگری شود

وقتی تیم‌های جداگانه مالک سهمیه‌ها و ظرفیت شوند، یا یک ماژول به چرخهٔ انتشار متفاوتی نیاز پیدا کند.
