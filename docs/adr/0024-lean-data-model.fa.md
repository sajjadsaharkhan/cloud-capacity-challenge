# ADR-0024: مدل دادهٔ کم‌حجم برای پیاده‌سازی تحویلی

- وضعیت: Accepted
- تاریخ: `2026-11-16`
- مرتبط: [پایگاه داده](../database/database.md)، [ADR-0008](0008-failure-mode-and-regional-cells.md)، [PRD A-13, A-18](../prd/PRD.md#7-assumptions)

## زمینه

صورت مسئله می‌گوید پیاده‌سازی تحویلی لازم نیست زیرساخت واقعی چندمنطقه‌ای یا بار عملیاتی شرکت را بازتولید کند، اما طراحی باید نشان دهد سیستم چطور می‌تواند در یک محیط واقعی رشد کند. یک پیش‌نویس قبلی 18 جدول داشت که بسیاری از آن‌ها فقط برای همان محیط واقعی وجود داشتند.

## تصمیم

نُه جدول و یک view در پیاده‌سازی: `pools`، `inventories`، `products`، `quotas`، `reservations`، `reservation_lines`، `reservation_events`، `ledger_entries`، `idempotency_keys`، و view با نام `reservation_effective`. هر چیزی که فقط در محیط واقعی لازم است به‌صورت یک گام رشد همراه با trigger مستند می‌شود، نه اینکه ساخته شود.

با وجود حجم، این‌ها نگه داشته شده‌اند چون درستی سیستم به آن‌ها وابسته است: ledger، کلیدهای idempotency، و counterها با CHECK constraint.

| حذف‌شده از پیش‌نویس | اکنون | چرا |
| --- | --- | --- |
| `regions`، `zones` | ستون‌های متنی روی `pools` که با configuration اعتبارسنجی می‌شوند | سه منطقهٔ ثابت به جدول نیاز ندارند |
| `resource_classes` | ستون متنی؛ تعریف در configuration | پنج کلاس بدون هیچ رفتاری در پایگاه داده |
| `customers` | حذف شد | هویت خارج از محدوده است؛ id از یک header می‌آید |
| `product_policies`، `product_resources` | ستون‌های `products` | رابطهٔ یک‌به‌یک و یک آرایه |
| `outbox` | در `reservation_events` ادغام شد | هر رویداد یک گذار است |
| `hold_cooldowns` | query روی `reservations` | از انقضاهای اخیر قابل استخراج است |
| `unmet_demand` | لاگ ساخت‌یافته و metric | تحلیل داده است، نه بخشی از تصمیم |
| partitionهای ماهانه روی ledger و رویدادها | جدول‌های ساده | در حجم تحویلی بی‌فایده است |

## گزینه‌های بررسی‌شده

| سطح | گزینه | نتیجه |
| --- | --- | --- |
| 1 | جدول‌های کمتر: حذف ledger، نگه‌داری idempotency در حافظه | رد شد. درستی و توضیح‌پذیری از دست می‌رود. |
| 2 | نُه جدول به‌علاوهٔ یک مسیر رشد مستند | **انتخاب‌شده** |
| 3 | مدل 18 جدولی با partitionها، جدول‌های مرجع و مشتری‌های سلسله‌مراتبی | برای پیاده‌سازی رد شد؛ اجزای آن همان مسیر رشد هستند. |

## پیامدها

- منطقه، zone و کلاس به‌جای foreign key با configuration برنامه اعتبارسنجی می‌شوند.
- هر گام رشد افزایشی است؛ هیچ‌کدام API یا ماشین‌های حالت را تغییر نمی‌دهد.

## چه زمانی بازنگری شود

هر ردیف از [مسیر رشد](../database/database.md#8-growth-path-to-the-real-environment) trigger مخصوص خودش را دارد.
