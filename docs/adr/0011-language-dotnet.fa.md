# ADR-0011: C# روی .NET 10 با ASP.NET Core

- وضعیت: Accepted
- تاریخ: `2026-11-16`
- مرتبط: [ADR-0013](0013-data-access-npgsql-dapper.md)، [معماری](../architecture/backend-architecture.md)

## زمینه

صورت مسئله هر زبانی را مجاز می‌داند و Go را امتیاز به حساب می‌آورد. تسلط نویسنده بر ASP.NET Core بیشتر از Go است.

## تصمیم

C# روی .NET 10، نسخهٔ LTS فعلی که تا نوامبر 2028 پشتیبانی می‌شود ([.NET support policy](https://dotnet.microsoft.com/platform/support/policy/dotnet-core)). ASP.NET Core Minimal APIs برای HTTP؛ `BackgroundService` برای نقش‌های sweeper و relay در همان host.

## گزینه‌های بررسی‌شده

| گزینه | نتیجه |
| --- | --- |
| C# / .NET 10 | **انتخاب شد.** درستی این سیستم در SQL و مدل تراکنش است، نه در زبان. تسلط، خطاهای هم‌زمانی و زمان تحویل را کم می‌کند و زمان بیشتری برای آزمون‌ها باقی می‌گذارد. Kestrel درخواست‌های در ثانیهٔ بسیار بیشتری از هدف 500/s پاسخ می‌دهد؛ در هر زبانی گلوگاه همان hot row پایگاه داده است. |
| Go | فقط به‌خاطر تسلط رد شد. برای یک سرویس زیرساختی کوچک گزینهٔ مناسب‌تری است و صورت مسئله هم آن را ترجیح می‌دهد. طراحی مستقل از زبان است: حدود 20 دستور SQL و دو ماشین حالت، که port کردنشان ارزان است. |
| Java / Kotlin | رد شد. نه ترجیح صورت مسئله است و نه تسلط نویسنده. |
| Python / Node.js | رد شد. typing ضعیف‌تر و مدل اجرای single-threaded برای سرویسی که ارزشش در درستی هم‌زمانی است ریسک اضافه می‌کند. |
| Rust | رد شد. سرعت توسعه. |

## پیامدها

- امتیاز صریح Go در ارزیابی از دست می‌رود.
- image بزرگ‌تر و حافظهٔ پایهٔ بیشتر نسبت به یک binary در Go.
- معادلی برای race detector در Go وجود ندارد؛ آزمون‌های یکپارچگی روی PostgreSQL واقعی هم‌زمانی را پوشش می‌دهند، یعنی همان جایی که raceهای این سیستم واقعاً رخ می‌دهند ([spec 11](../specs/11-testing.md)).

## چه زمانی بازنگری شود

وقتی تیمی که سرویس را نگهداری می‌کند Go-محور باشد.
