# واژه‌نامه

همهٔ واژه‌های خاص این پروژه که در این راهنما به کار رفته‌اند، به زبان ساده. واژه‌ها بر اساس موضوع گروه‌بندی شده‌اند و هر گروه به فصلی پیوند دارد که آن واژه‌ها بیشترین اهمیت را در آن دارند.

## ظرفیت و منابع

| واژه | معنا |
| --- | --- |
| **Resource class** | یک نوع ظرفیت: `Vcpu` (millicore)، `RamMb` (مگابایت)، `DiskGb` (گیگابایت)، `Ipv4` (آدرس)، `Gpu` (کارت). همیشه به‌صورت عدد صحیح در همان واحد پایه شمرده می‌شود |
| **Scope** | سطحی که یک class در آن شمرده می‌شود: **zone** برای CPU، RAM و دیسک؛ **منطقه (region)** برای IPv4؛ **host** برای GPU |
| **منطقه / zone** | یک ناحیهٔ دیتاسنتر (`ir-thr`، `ir-tbz`، `ir-ahv`) و بخشی از آن (`ir-thr-1`). هر درخواست دقیقاً یک منطقه را هدف می‌گیرد |
| **Pool** | یک واحد حساب‌وکتاب ظرفیت: یک منطقه، یک zone یا یک host منفرد. یک وضعیت ادمین دارد (`Registered`، `Available`، `Offline`، `Retired`) |
| **Inventory** | یک سطر به ازای هر (pool، resource class) که `total`، `reserved`، `allocation_ratio`، محدودیت‌های اندازه و دو شمارندهٔ `held` و `used` را نگه می‌دارد |
| **Total** | تعداد واحدهای فیزیکی pool برای آن class |
| **Reserved (حاشیه)** | واحدهایی که عمداً هرگز فروخته نمی‌شوند، حدود 10% یک zone، تا **fragmentation** را جذب کنند |
| **Allocation ratio** | ضریب overcommit (≥ 1). نسبت 4 یعنی هر هستهٔ فیزیکی چهار بار فروخته می‌شود |
| **ظرفیت قابل فروش (sellable)** | `floor((total − reserved) × allocation_ratio)`. بیشترین مقداری که مجموع held و used هرگز می‌تواند به آن برسد |
| **Held** | واحدهایی که در یک hold کوتاه‌مدت (یک lease) هستند و هنوز تأیید نشده‌اند |
| **Used** | واحدهایی که تأیید شده و به یک سرویس زنده تخصیص یافته‌اند |
| **Free** | `sellable − held − used`، فقط روی یک pool در وضعیت `Available` |
| **Effective free** | Free به‌علاوهٔ واحدهایی که هنوز به‌عنوان held شمرده می‌شوند اما مهلت holdشان **گذشته است** |
| **سطح ظرفیت** | آنچه مشتری‌ها به‌جای عدد می‌بینند: `Available`، `Limited` (کمتر از 10% آزاد)، `Unavailable` |
| **Fit-check** | یک فراخوانی مشورتی «آیا این همین الان، با در نظر گرفتن سهمیهٔ من، جا می‌شود؟». هرگز چیزی را رزرو نمی‌کند |
| **Fragmentation** | شمارنده‌ها می‌گویند 100 هسته آزاد است، اما هیچ hostی 16 هسته را یک‌جا ندارد. مدل شمارنده‌ای این را نمی‌بیند؛ حاشیه آن را پوشش می‌دهد |
| **Hot row** | یک سطر inventory که درخواست‌های زیادی هم‌زمان آن را به‌روز می‌کنند. قفل آن سقف واقعی throughput است |
| **Round trip** | یک درخواست از سرویس به PostgreSQL و پاسخ آن. یک hold به 9 round trip نیاز دارد (از 28 کاهش یافته)؛ hot row فقط برای آخرین `UPDATE` و commit قفل می‌شود |

ببینید: [مدل داده](#05-data-model) و [منطق اصلی](#07-core-logic).

## رزروها

| واژه | معنا |
| --- | --- |
| **رزرو (Reservation)** | یک درخواست مشتری برای ظرفیت، با ماشین حالت خودش. در specها *request* نامیده می‌شود |
| **Line (سطر)** | یک جفت (resource class، مقدار) درون یک رزرو. هر رزرو 1 تا 16 سطر دارد |
| **Hold** | کنار گذاشتن ظرفیت برای مدتی کوتاه، به‌صورت اتمی برای همهٔ سطرها. نتیجه: وضعیت `Held` |
| **Lease / TTL** | طول عمر hold (پیش‌فرض 15 دقیقه، به ازای هر محصول). در `expires_at` تمام می‌شود |
| **Confirm** | تبدیل یک hold به تخصیص (`held → used`) پیش از پایان lease. سپس سرویس محصول provision می‌کند |
| **Cancel** | پس دادن داوطلبانهٔ یک hold یا یک انتظار |
| **Extend** | افزودن یک TTL دیگر به یک hold. فقط **یک بار** مجاز است |
| **Expire** | رویداد تایمر: holdی که از `expires_at` گذشته به `Expired` تبدیل می‌شود و ظرفیتش برمی‌گردد |
| **Release** | آزاد کردن ظرفیت *تأییدشده* وقتی سرویس حذف شده یا provisioning شکست خورده است (`used` کم می‌شود). سرویس‌های محصول آن را صدا می‌زنند |
| **Allocation state** | `Active` یا `Released`، فقط روی رزرو تأییدشده. release این را تغییر می‌دهد، نه وضعیت رزرو را |
| **Wait / Waiting (انتظار)** | پارک کردن اختیاری (`onShortage: Wait`) برای یک کمبود **موقت**، حداکثر 15 دقیقه. چیزی را hold نمی‌کند |
| **Promote (ارتقا)** | انتقال یک رزرو منتظر به `Held` وقتی ظرفیت برمی‌گردد، قدیمی‌ترین اول |
| **Timeout** | رویداد تایمر برای انتظاری که از مهلتش گذشته است: به `Rejected` (`WaitTimeout`) تبدیل می‌شود |
| **همه یا هیچ (All-or-nothing)** | یا همهٔ سطرها hold می‌شوند یا هیچ‌کدام. با یک savepoint پایگاه داده پیاده‌سازی شده |
| **Client reference** | یک شناسهٔ اختیاری از سمت کلاینت (مثلاً شمارهٔ سفارش)، یکتا در میان رزروهای باز و تأییدشده. محافظ دوم در برابر تکرار |
| **Try-confirm-cancel** | قرارداد با سرویس‌های محصول: hold، provision **پس از** confirm، و release هنگام حذف |

ببینید: [ماشین‌های حالت](#06-state-machines).

## پاسخ‌های کمبود

| کد | معنا | retry کمک می‌کند؟ |
| --- | --- | --- |
| **ExceedsRegisteredCapacity** | بزرگ‌تر از چیزی که هیچ poolی هرگز بتواند فراهم کند | هرگز |
| **CapacitySoldOut** | در تئوری جا می‌شود، اما تخصیص‌های تأییدشده آن را پر کرده‌اند | نه در یک بازهٔ زمانی مشخص |
| **CapacityTemporarilyUnavailable** | فقط به‌خاطر holdهای باز یا یک pool آفلاین کم است | بله، در طول یک TTL (`Retry-After`) |
| **QuotaExceeded** | فراتر از قرارداد مشتری | فقط پس از کم شدن مصرف خود او |
| **PoolShareExceeded** | فراتر از سهم مشتری از یک pool کمیاب | فقط پس از کم شدن مصرف خود او |

## وضعیت و زمان

| واژه | معنا |
| --- | --- |
| **DFA** | خودکارهٔ متناهی قطعی (Deterministic finite automaton): مجموعه‌ای ثابت از حالت‌ها و جدولی از حرکت‌های مجاز. هر جفت (حالت، رویداد) دقیقاً یک نتیجه دارد یا رد می‌شود |
| **Request DFA** | ماشین حالت رزرو: `New → Waiting / Held → Confirmed / Rejected / Cancelled / Expired` |
| **Resource DFA** | ماشین حالت یک واحد ظرفیت: `Registered → Available → Held → Allocated → …`، که به‌صورت شمارنده ذخیره می‌شود، نه سطر |
| **Stored status** | ستون وضعیت در پایگاه داده |
| **Effective status** | آنچه **همین الان** درست است: یک `Held` ذخیره‌شده که مهلتش گذشته، *در واقع* `Expired` است. همهٔ خواندن‌ها این را برمی‌گردانند |
| **Settled** | `true` وقتی وضعیت ذخیره‌شده و مؤثر یکی باشند؛ `false` تا وقتی رزروی که مهلتش گذشته منتظر sweeper است |
| **Guard** | شرطی که یک گذار را مجاز می‌کند، مثلاً `now < expires_at` برای confirm |
| **ساعت پایگاه داده** | `now()` تراکنش از PostgreSQL. تنها ساعتی که هر تصمیمی از آن استفاده می‌کند؛ ساعت سرورها نادیده گرفته می‌شود |
| **Version** | یک شمارنده روی هر رزرو که با هر گذار 1 واحد زیاد می‌شود. برای به‌روزرسانی امن و ترتیب‌دهی رویدادها استفاده می‌شود |

## نقش‌های پس‌زمینه

| واژه | معنا |
| --- | --- |
| **Role (نقش)** | یکی از سه شیوه‌ای که همان image اجرا می‌شود: `api`، `sweeper`، `relay` |
| **Sweeper** | worker پس‌زمینه‌ای که هر ثانیه اجرا می‌شود. holdهایی را که از lease خود گذشته‌اند **منقضی** می‌کند، انتظارها را **timeout** می‌کند، منتظرها را **ارتقا** می‌دهد، کلیدهای قدیمی idempotency را **پاک** می‌کند و **reconciliation ساعتی** را محاسبه می‌کند. در batchهای 200تایی با `SKIP LOCKED` کار می‌کند، پس چند sweeper می‌توانند با امنیت اجرا شوند |
| **Inline finalizer** | sweeper کوچکِ خودِ مسیر hold: وقتی یک ثبت فقط به این دلیل کم می‌آورد که holdهای منقضی‌شده هنوز sweep نشده‌اند، آن holdها را نهایی می‌کند و **یک بار** دوباره تلاش می‌کند |
| **Relay** | worker پس‌زمینه‌ای که سطرهای منتشرنشده را از outbox می‌خواند، در RabbitMQ منتشر می‌کند و سپس آن‌ها را منتشرشده علامت می‌زند |
| **Outbox (تراکنشی)** | نوشتن سطر رویداد در **همان تراکنشی** که تغییر وضعیت در آن انجام می‌شود، تا یک رویداد وجود داشته باشد اگر و تنها اگر تغییر commit شده باشد. اینجا outbox همان جدول `reservation_events` است که تاریخچه هم هست |
| **تحویل حداقل یک‌باره (At-least-once delivery)** | یک رویداد ممکن است دو بار منتشر شود (مثلاً relay پس از انتشار crash کرده باشد). مصرف‌کننده‌ها با شناسهٔ رویداد تکرار را حذف می‌کنند |
| **Migrator** | فرمان یک‌بارهٔ `migrate` که migrationهای پایگاه داده (DbUp) را پیش از شروع نقش‌ها اعمال می‌کند |

ببینید: [منطق اصلی](#07-core-logic).

## تکنیک‌های درستی

| واژه | معنا |
| --- | --- |
| **به‌روزرسانی شرطی (Conditional update)** | `UPDATE … SET held = held + q WHERE held + used + q <= sellable`. تغییر یک سطر یعنی موفقیت؛ صفر سطر یعنی کمبود. هیچ شکافی بین خواندن و نوشتن نیست |
| **قید CHECK** | قاعده‌ای که خود پایگاه داده روی هر سطر اعمال می‌کند (مثلاً `held + used <= sellable`). آخرین خط دفاع اگر کد اشتباه کند |
| **ترتیب سراسری قفل‌گذاری** | هر نویسنده سطرها را با یک ترتیب قفل می‌کند: reservation → quota → inventory، هر کدام مرتب‌شده. این کار deadlock را ناممکن می‌کند |
| **Savepoint** | نشانه‌ای درون یک تراکنش که می‌توان به آن rollback کرد بی‌آنکه کل تراکنش abort شود. برای امتحان zone یا host بعدی استفاده می‌شود |
| **`FOR UPDATE SKIP LOCKED`** | «این سطرها را قفل کن و هر سطری را که worker دیگری قبلاً قفل کرده رد کن.» به چند sweeper یا relay اجازه می‌دهد بدون انتظار کار را بین خود تقسیم کنند |
| **`READ COMMITTED`** | سطح ایزولیشن PostgreSQL که استفاده شده است. همراه با به‌روزرسانی‌های شرطی کافی است، بدون retryهای `SERIALIZABLE` |
| **Ledger** | جدول فقط‌افزودنی `ledger_entries`. هر تغییر در `held` یا `used` یک سطر می‌نویسد (`HOLD`، `COMMIT`، `RETURN`، `RELEASE`، `ADJUST`). **منبع حقیقت** |
| **شمارنده (Counter)** | `held` و `used` روی inventoryها و سهمیه‌ها. یک projection سریع از ledger که در همان تراکنش به‌روز می‌شود |
| **Reconciliation** | محاسبهٔ دوبارهٔ شمارنده‌ها از روی ledger و رزروها و گزارش هر اختلاف |
| **Drift** | اختلافی که reconciliation پیدا می‌کند. هدف: 0 سطر |
| **ADJUST** | سطری در ledger که یک اپراتور برای اصلاح drift می‌نویسد. تنها راه تغییر دستی یک شمارنده |
| **Fail closed** | وقتی مطمئن نیستیم (مثلاً پایگاه داده در دسترس نیست)، رد کن به‌جای اینکه ریسک بیش‌فروشی را بپذیری |
| **Negative cache (sold-out)** | به خاطر سپردن sold-out بودن یک pool برای 1 ثانیه، تا درخواست‌های بعدی از hot row عبور نکنند و ارزان رد شوند |

## Retryها

| واژه | معنا |
| --- | --- |
| **Idempotency** | فرستادن یک درخواست برای دو بار همان اثر یک بار فرستادن را دارد |
| **کلید idempotency** | header `Idempotency-Key`. به ازای هر مشتری همراه با پاسخ ذخیره می‌شود، در همان تراکنشی که کار در آن انجام می‌شود |
| **Fingerprint** | SHA-256 نام عملیات و بدنهٔ درخواست. کلیدی که دوباره با fingerprint متفاوت استفاده شود رد می‌شود (`422`) |
| **Replay** | برگرداندن پاسخ ذخیره‌شده برای یک کلید تکراری، با علامت `Idempotent-Replayed: true` |
| **Retry-After** | headerی که به کلاینت می‌گوید چند ثانیه پیش از retry صبر کند |

ببینید: [Idempotency](#08-idempotency).

## محدودیت‌ها و انصاف

| واژه | معنا |
| --- | --- |
| **سهمیه (Quota)** | حد قراردادی یک مشتری به ازای (resource class، منطقه). holdهای باز از آن کم می‌شوند |
| **Token bucket** | الگوریتم محدودیت نرخ: سطلی با N توکن که با نرخ ثابت پر می‌شود؛ هر درخواست یک توکن برمی‌دارد و سطل خالی یعنی `429` |
| **Rate group** | اینکه یک endpoint از کدام سطل استفاده می‌کند: `submit`، `fitcheck`، `reads`، `transitions` |
| **Hold limit** | حداکثر holdهای فعال به ازای هر مشتری و محصول |
| **Waiting limit** | حداکثر رزروهای منتظر به ازای هر مشتری و محصول (4) |
| **Pool share cap** | روی محصولات کمیاب، حداکثر سهمی از یک pool که یک مشتری می‌تواند hold کند (25%) |
| **Cooldown** | پس از 5 hold منقضی‌شده در یک ساعت، یک وقفهٔ 10 دقیقه‌ای روی holdهای جدید برای آن محصول |
| **احتکار (Hoarding)** | گرفتن hold فقط برای اینکه ظرفیت به دست دیگران نرسد. share cap، hold limit و cooldown برای مقابله با آن وجود دارند |

ببینید: [محدودیت نرخ و انصاف](#09-rate-limits-fairness).

## بازیگران

| واژه | معنا |
| --- | --- |
| **Gateway** | API gateway جلوی این سرویس. احراز هویت می‌کند و headerهای هویتی مورد اعتماد را عبور می‌دهد |
| **مشتری (Customer)** | `X-Actor-Kind: Customer`. کاربر پنل یا اتوماسیون او |
| **Service** | `X-Actor-Kind: Service`. یک سرویس داخلی محصول (VM، DBaaS، IP) که از طرف مشتری عمل می‌کند؛ تنها فراخوان release غیر از ادمین‌ها |
| **ادمین (Admin)** | `X-Actor-Kind: Admin`. یک اپراتور ظرفیت که از admin API استفاده می‌کند |
| **سرویس محصول** | سیستمی که واقعاً VM یا IP را می‌سازد. holdها را confirm می‌کند و ظرفیت را release می‌کند |

## معماری و کد

| واژه | معنا |
| --- | --- |
| **Monolith ماژولار** | یک codebase و یک image قابل استقرار که درونش به ماژول‌ها تقسیم شده است، به‌جای microservice |
| **Clean architecture** | لایه‌هایی که لایه‌های درونی هرگز به لایه‌های بیرونی وابسته نیستند: Domain ← Application ← Infrastructure، Presentation |
| **UseCase** | یک عملیات کسب‌وکاری، و تنها کدی که اجازه دارد مالک یک تراکنش باشد |
| **Flow** | یک دنباله روی دو یا چند aggregate که درون تراکنش UseCase اجرا می‌شود (مثلاً `ExpireHeldFlow` که بین submit و sweeper مشترک است) |
| **Operation** | کار روی یک aggregate از طریق repository آن |
| **Port** | interfaceی که لایهٔ Application تعریف و Infrastructure پیاده‌سازی می‌کند (مثلاً repository مربوط به capacity ledger) |
| **Aggregate** | خوشه‌ای از داده که به‌صورت یک واحد تغییر می‌کند؛ اینجا یک رزرو همراه با سطرهایش |
| **ApiResult envelope** | شکل مشترک JSON یعنی `{ isSuccess, data, error, traceId }` در همهٔ پاسخ‌ها |
| **سلول منطقه‌ای (Regional cell)** | یک نسخهٔ کامل از سیستم (پایگاه داده به‌علاوهٔ نقش‌ها) که دقیقاً به یک منطقه سرویس می‌دهد |
| **ADR** | Architecture Decision Record: یک تصمیم، گزینه‌های ردشده و اینکه کی باید در آن بازنگری کرد |

## عملیات و مقیاس

| واژه | معنا |
| --- | --- |
| **RPO** | Recovery Point Objective: چه مقدار دادهٔ commit‌شده ممکن است در یک خرابی از دست برود. هدف 0 |
| **RTO** | Recovery Time Objective: چقدر طول می‌کشد تا سرویس برگردد. هدف زیر 60 s |
| **Replication هم‌گام** | یک commit فقط پس از آنکه یک standby آن را دریافت کرد تأیید می‌شود، پس crash شدن primary چیزی را از دست نمی‌دهد |
| **Failover** | ارتقای یک standby وقتی primary از کار می‌افتد |
| **Escrow** | تقسیم ظرفیت یک pool به برش‌های مستقل تا بتوان آن‌ها را به‌صورت موازی به‌روز کرد. یک گام مقیاس در آینده |
| **CDC** | Change Data Capture: استریم کردن تغییرات پایگاه داده. جایگزینی آینده برای relay در حجم بالای رویداد |
| **p50 / p99** | تأخیری که 50% / 99% درخواست‌ها زیر آن می‌مانند |
| **k6** | ابزار آزمون بار که در `load/k6/` استفاده شده است |
| **Testcontainers** | کتابخانه‌ای که برای هر اجرای آزمون یک PostgreSQL واقعی در Docker راه‌اندازی می‌کند |
