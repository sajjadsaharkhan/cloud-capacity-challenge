Hold latency: where it goes, and the plan to meet 150 ms

Cloud Capacity Allocation · report of 2026-11-16 · based on the running implementation (make up stack) and measurements taken for this report

The service is correct under every load tried (no oversell, zero ledger drift), and meets the 150 ms p99 target at the modelled peak. It does not meet it once one inventory row is pushed past about 150 holds/s, and the rejection path collapses past about 150 requests/s. The cause is structural: a hold costs 28 network round trips, and the contended row stays locked for the last 7 of them.

1 · Current architecture of a hold request

A POST /v1/reservations runs as one SubmitReservationUseCase. It owns a single READ COMMITTED transaction, asks the Operations to validate and plan, then tries each plan under a savepoint until one conditional UPDATE succeeds. Nothing outside PostgreSQL is on the decision path; the broker is fed afterwards from the outbox.

What the database was doing

  • Under rejection load at 150/s, PostgreSQL used about 4.4 of 8 cores (the api about 1.4). With statement auto-preparation and no connection reset, the same offered load used about 1.7 cores, and p99 at 100/s fell from 188 ms to 39 ms.
  • At 200/s nearly every backend was "idle in transaction, waiting on the client". The database was not busy; transactions were queueing behind a chatty client protocol. That is the signature of too many round trips, not of too little database.
  • Correctness never moved. The 2-minute scarce burst granted exactly 200 holds on a 200-unit pool, with zero drift afterwards. Overload shows up as latency and 503s, never as oversell.
Caveat. The first step of each run includes JIT warm-up, which is why the 5/s tail looks worse than 20/s in the experiment series. Docker Desktop adds network and fsync cost that a Linux host would not. The baseline must be re-taken on the target hardware before committing to numbers; the plan below is ordered by evidence, not by promised speed-ups.

3 · The plan

Goal. p99 < 150 ms for a hold at 150 holds/s on one inventory row (the ADR-0004 safe limit), p99 < 150 ms and 5xx < 0.05% for the 300/s scarce burst (most of it rejected), and ≥ 500 holds/s per cell across the pools of a region, with zero oversell throughout. The strategy has one idea: do less per hold, and lock the contended row for as little as possible.

4 · Order of work and how we will know

  1. P0, then P1 and P4 first: smallest changes, and they remove the rejection-path collapse that dominates a burst.
  2. P2 then P3: the bulk of the latency and per-row throughput gain, still in C# and still covered by the current tests.
  3. Re-measure. If hot-row p99 at 150/s is under 150 ms on target hardware, stop there and keep P6 as the next step. If not, do P5/P6.
  4. P7 alongside, since it caps the worst case regardless of the rest. P8 only when the existing hot-row alert fires; it is a data change.

5 · Honest limits of this report

  • One machine, one api replica, Docker Desktop: the absolute numbers are not the production numbers. The comparison between configurations is what to trust.
  • The 8 → 4 trip and lock-window figures for P5–P6 are design counts; the throughput they unlock is proportional in theory and must be measured.
  • The earlier scarce-burst run mixed a quota PUT into every iteration, which doubled the request count and added writes; it overstates the problem. The per-step series above isolates the hold.
  • Not yet measured: expiry-storm.js, mixed.js, a multi-replica api, and synchronous replication.
